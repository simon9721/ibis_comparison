# Xyce pybis2spice benches

This folder mirrors the working `ngspice_pybis` benches with Xyce-compatible
output directives and channel syntax.

Use:

```powershell
& 'C:\Program Files\XyceNF_7.10\bin\Xyce.exe' .\tb_validation_pulse_xyce_pybis.cir
```

## Files

- `driver_OutputInput_Typical.sub` - copied from `ngspice_pybis`.
- `channel_xyce.sp` - same 10-section 50-ohm RLGC ladder, with the shunt
  conductance represented as 1 Mohm resistors for portable Xyce syntax.
- `tb_validation_pulse_xyce_pybis.cir` - compact 20 ns pulse validation.
- `tb_pybis_prbs7_new50ohm_xyce.cir` - 1000 ns PRBS7 + new 50-ohm channel.

## Current Finding

The direct Xyce syntax port parses, but simple pybis decks fail DCOP unless
`uic` is used, and sharp input transitions can trigger timestep traps.

For Xyce numerical experiments, use:

- `driver_OutputInput_Typical_xyce_relaxed.sub`

This copy relaxes the internal gates from `tanh(200*...)` to `tanh(20*...)`.
It is not yet an accuracy-approved model, but it allows simple deterministic
cases to complete:

- `tb_test_rise_late_xyce_uic_relaxed.cir`
- `tb_test_rfr_xyce_uic_relaxed.cir`
- `tb_test_rfall_late_xyce_uic_relaxed.cir`
- `tb_validation_pulse_200p_tline_xyce_relaxed.cir`
- `tb_channel_rise_200p_xyce_relaxed.cir`
- `tb_channel_rfr_200p_xyce_relaxed.cir`
- `tb_channel_twopulse_200p_xyce_relaxed.cir`

The repeated pulse train is still a boundary for that `tanh20` model:

- `tb_channel_pulsetrain_200p_xyce_relaxed.cir` wrote data to `26.671 ns`
  before the run was killed after `90 s`

For a more aggressive numerical diagnostic, use:

- `driver_OutputInput_Typical_xyce_relaxed10.sub`
- `tb_channel_pulsetrain_200p_xyce_relaxed10.cir`

That pair relaxes the same gates to `tanh(10*...)` and completes the 40 ns
repeated pulse-train case. Treat it as a solver-continuation experiment until
it is compared against the ngspice pybis waveforms.

A smoothing sweep found the current repeated-switching bracket:

- `tanh20`, `tanh18`, `tanh17`, and `tanh16` did not complete the 40 ns pulse
  train within the timeout
- `tanh15`, `tanh12`, and `tanh10` completed

The first passing bracket point is:

- `driver_OutputInput_Typical_xyce_relaxed15.sub`
- `tb_channel_pulsetrain_200p_xyce_relaxed15.cir`

A short deterministic non-PRBS bit-pattern case also passes with `tanh15`:

- `tb_channel_bitpattern_200p_xyce_relaxed15.cir`
- pattern: `1 0 1 1 0 0 1 0`, 5 ns UI, 200 ps edges
- final time: `45 ns`

## Best Current Xyce pybis Setup

The most useful Xyce time-integration option block found so far is:

```spice
.options timeint method=trap maxord=1 erroption=1 delmax=20p nlmin=3 nlmax=8 timestepsreversal=1
```

This uses Backward-Euler plus non-LTE timestep control. It came from the Xyce
user-guide guidance that Gear/Backward-Euler can help convergence and that
`ERROPTION=1` should be paired with `DELMAX`.

Current practical status:

- direct unrelaxed pybis + this option block now passes simple delayed Rload
  rise and rise/fall cases
- direct unrelaxed pybis still does not complete repeated channel switching
- `tanh20` relaxed pybis + this option block completes deterministic repeated
  pulse train, deterministic bit pattern, and a 100 ns PRBS diagnostic
- `tanh20` still does not complete the full 1000 ns PRBS run
- `tanh15` relaxed pybis + this option block completes the full 1000 ns PRBS7
  run on the new 50-ohm RLGC channel
- a newer localized long-PRBS profile, `edge15_flat4p2`, keeps the final
  `Ku/Kd` selector at `tanh92`, relaxes only the edge/latch block to `tanh15`,
  and flattens the rising `KUR/KDR` table tail after `4.2 ns`; it completes
  1000 ns PRBS with much lower RMSE than the older all-`tanh15` fallback

Best full PRBS candidate generated by the tail-fix experiments:

- `tb_tailfix_channel_prbs7_1000n_edge15_flat4p2.cir`

Result against ngspice direct pybis:

- final time: `1000 ns`
- runtime: `4.78 s`
- `V(n10b)` RMSE: `26.6 mV`

Older full PRBS fallback:

- `tb_pybis_prbs7_new50ohm_xyce_relaxed15_timeint_nlte_be_1000n.cir`

Result:

- final time: `1000 ns`
- runtime: `4.44 s`
- `V(n10b)` range: `0 V` to `1.539 V`
- `V(n10b)` RMSE in the tail-fix harness: `75.1 mV`

Important caveat: `edge15_flat4p2` is a long-PRBS/channel profile, not a
universal small-bench replacement. It passes the 26 ns RFR T-line case and the
full 1000 ns PRBS case, but it times out on the periodic `pulse200p` ideal
T-line gate at about `14.95 ns`.

## Minimal-Modification Findings

The direct pybis model uses `tanh(200*...)` gates. Larger relaxed factors are
therefore closer to the unmodified pybis model.

With the best current Xyce timestep options, the 40 ns repeated pulse train now
passes as high as:

- `driver_OutputInput_Typical_xyce_relaxed92.sub`
- `tb_channel_pulsetrain_200p_xyce_relaxed92_timeint_nlte_be.cir`

But the behavior is non-monotonic:

- deterministic passes: `tanh20`, `tanh50`, `tanh75`, `tanh90`, `tanh92`
- deterministic timeouts: direct `tanh200`, `tanh100`, `tanh98`, `tanh95`,
  `tanh94`, `tanh60`, `tanh30`

For PRBS:

- `tanh50` passes the 200 ns PRBS diagnostic
- `tanh50` does not complete 1000 ns; even with `.options output initial_interval=10p`
  it stalls at `205.270 ns`
- `tanh75` and `tanh90` do not pass the 200 ns PRBS diagnostic
- `edge50_flat4p2` passes the 200 ns PRBS diagnostic but stalls at
  `205.270 ns` on the 1000 ns run
- `edge15_flat4p2` passes the full 1000 ns PRBS run and is much closer to
  ngspice than the older all-`tanh15` fallback

Output throttling:

```spice
.options output initial_interval=10p
```

This dramatically reduces CSV size for high-step-count runs, but it does not by
itself fix the solver stall.

## SPISim-Style Validation Matrix

The repeatable small-bench validation runner is:

```powershell
python ..\scripts\run_spisim_style_pybis_validation.py --timeout 30
```

To rebuild metrics/plots from existing raw/CSV data:

```powershell
python ..\scripts\run_spisim_style_pybis_validation.py --dry-run
```

This generates SPISim-style ideal 30 ps, 50 ohm T-line benches:

- `pulse5p`: SPISim-like periodic pulse with 5 ps edges
- `pulse200p`: same topology with practical 200 ps edges
- `rfr5p`: rise-fall-rise sequence with 5 ps edges
- `rfr200p`: rise-fall-rise sequence with practical 200 ps edges

Current lesson:

- ngspice direct pybis completes all four small T-line baselines quickly when
  run in SPISim style with normal operating-point setup and minimal probes
- Xyce direct pybis does not complete even the practical 200 ps T-line pulse
- Xyce relaxed models `tanh92`, `tanh50`, `tanh20`, and `tanh15` complete the
  practical 200 ps single-pulse T-line validation
- Xyce 5 ps SPISim edges remain a stress diagnostic, not a fair acceptance gate
  for the Xyce pybis flow
- Xyce 200 ps rise-fall-rise T-line cases still stall around `22 ns`, so the
  repeated-transition difficulty is already visible before the full RLGC
  channel or PRBS stimulus

The best lightweight acceptance test for a new Xyce pybis candidate is now:

1. `pulse200p` ideal T-line pass
2. `rfr200p` ideal T-line progress/partial waveform review
3. deterministic RLGC pulse train
4. PRBS only after the previous cases are understood

## Root-Cause Finding

The root-cause probe runner is:

```powershell
python ..\scripts\probe_xyce_pybis_root_cause.py --timeout 30
```

Most useful root-cause results for `tanh92` on the practical 200 ps
rise-fall-rise ideal-T-line bench:

- stopping at `21 ns` passes in about `2.6 s`, with `NX=3.91 ns`
- stopping at `22 ns` times out at about `21.89 ns`, with `NX=4.80 ns`
- reducing `.print` output to only input/pad/far-end still times out at the
  same point
- loosening `DELMAX` from `20p` to `100p` still times out at the same point
- capping the internal `NX` coefficient-clock at `4.0`, `4.1`, or `4.2 ns`
  makes the full `26 ns` bench pass in about `3.3 s`
- capping `NX` at `4.3 ns` or higher does not robustly pass
- keeping `NX` normal but capping both rising waveform coefficient lookups
  `KUR` and `KDR` at `4.2 ns` also makes the full `26 ns` bench pass
- capping only `KUR` or only `KDR` is not enough

Conclusion: the main ideal-T-line RFR stall is caused by Xyce spending
pathological time in the late rising waveform coefficient-table tail, around
`NX=4.2-4.8 ns`. It is not caused by CSV output volume, the requested transient
stop time, or the external T-line by itself.

The `KUR/KDR` cap is only an experiment right now. It proves the root cause but
should not yet be treated as an accuracy-approved model change.

## Tail-Fix Experiments

The follow-up fix-direction runner is:

```powershell
python ..\scripts\test_xyce_pybis_tail_fixes.py --stage tline --candidates all
python ..\scripts\summarize_xyce_tailfix_results.py
```

Main findings:

- hard-capping or flattening both rising `KUR/KDR` table lookups at `4.2 ns`
  fixes the `tanh92` RFR200p T-line stall; hard and flat versions are
  numerically equivalent in the tested cases
- softer tail caps with `k=5` or `k=10` still time out; `k=20` passes, so the
  useful "soft" cap is effectively sharp
- tail conditioning alone does not fix PRBS: `hard4p2` stalls at `70.2 ns`
  on the 200 ns PRBS run
- relaxing only the edge/latch block (`B10-B18`) matters for PRBS; relaxing
  only the final selector block (`B24-B29`) still stalls at `70.2 ns`
- `edge50_flat4p2` is the best short-PRBS/T-line compromise found so far:
  it passes both 200 ps T-line gates, deterministic channel gates, and 200 ns
  PRBS, but it still stalls at `205.27 ns` on 1000 ns PRBS
- `edge15_flat4p2` is the best long-PRBS/channel profile found so far:
  1000 ns PRBS passes in `4.78 s` with `26.6 mV` RMSE vs ngspice, compared
  with `75.1 mV` for the old all-`tanh15` model
- no single profile tested so far passes every small T-line gate and the full
  PRBS gate

## PRBS + Ideal T-Line Stress Case

The missing middle case runner is:

```powershell
python ..\scripts\run_xyce_pybis_prbs_tline.py --stop 100n --candidates tanh92,flat4p2,edge50_flat4p2,edge15_flat4p2
```

This uses the PRBS7 voltage source, the pybis driver, an ideal 30 ps 50-ohm
T-line, and a 50-ohm far-end load.

New finding: this is a stress case for both simulators, not just Xyce.

| Case | Result |
|---|---|
| ngspice direct pybis, stop `100 ns` | pass in `2.11 s` |
| ngspice direct pybis, stop `120 ns` | pass in `3.03 s` |
| ngspice direct pybis, stop `130 ns` | timeout at `125.56 ns` after `90 s` |
| ngspice direct pybis, stop `200 ns` | timeout at `125.58 ns` after `180 s` |
| Xyce `tanh92`, stop `100 ns` | timeout/progress only to `65.25 ns` |
| Xyce `flat4p2`, stop `100 ns` | timeout/progress only to `65.44 ns` |
| Xyce `edge50_flat4p2`, stop `100 ns` | best progress, but timeout at `95.44 ns` |
| Xyce `edge15_flat4p2`, stop `100 ns` | timeout/progress only to `45.08 ns` |

Additional line-specific probes showed that relaxing only `B18`, only
`B17/B18`, or `B15/B17/B18` to `tanh15` still stalls around `65.4 ns`.
Relaxing only the threshold gates `B10/B11` to `tanh15` is worse, reaching only
`35.4 ns`.

Interpretation: the ideal lossless T-line PRBS case is a harsher numerical
stress than the matched RLGC-channel PRBS case. It is useful as a stress probe,
but the current accepted long-run comparison should remain the RLGC-channel
PRBS1000 case unless the ideal-T-line setup is further conditioned or bracketed.

### Source-Damping Sweep

The same runner now supports driver-to-line series damping:

```powershell
python ..\scripts\run_xyce_pybis_prbs_tline.py --stop 200n --riso 2 --candidates edge50_flat4p2
```

Ngspice direct pybis on PRBS + ideal T-line:

| `RISO` | `130 ns` result | `200 ns` result |
|---:|---|---|
| `0 ohm` | timeout at `125.56 ns` | timeout at `125.58 ns` |
| `0.1 ohm` | timeout at `125.55 ns` | not run |
| `0.5 ohm` | timeout at `110.31 ns` | not run |
| `1.0 ohm` | timeout at `125.60 ns` | not run |
| `1.25 ohm` | timeout at `125.60 ns` | not run |
| `1.5 ohm` | timeout at `105.47 ns` | not run |
| `1.75 ohm` | pass | pass to `200 ns` |
| `2.0 ohm` | pass | pass to `200 ns` |
| `5.0 ohm` | not run | timeout at `109.99 ns` |

Xyce `edge50_flat4p2`:

| `RISO` | Result |
|---:|---|
| `0 ohm`, stop `100 ns` | timeout at `95.44 ns` |
| `2.0 ohm`, stop `100 ns` | pass in `8.19 s`, RMSE `45.2 mV` |
| `1.75 ohm`, stop `200 ns` | timeout at `67.69 ns` |
| `2.0 ohm`, stop `200 ns` | timeout at `106.06 ns` |

Interpretation: modest source damping confirms that the ideal PRBS/T-line
problem is strongly tied to the too-ideal lossless load topology. It can rescue
ngspice through `200 ns` in a narrow `RISO` window around `1.75-2 ohm`, and it
rescues Xyce `edge50_flat4p2` through `100 ns`. It does not yet give Xyce a
full `200 ns` PRBS/T-line pass.
